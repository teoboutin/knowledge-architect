# Agent skills design: The retrospective

## The retrospective

### An unrecognised transcript line reaches this repository through the command's header, the transcript reviewer's report and the retrospective's item on the checker `##unrecognised-entries-reach-upstream`

The header of `klarch transcript` ends, where it names any line or value it does not recognise, with
the line asking for each to be reported as a finding on the checker in the retrospective, per
`design@core@transcript-format-tolerated-and-reported`. The transcript reviewer lists each such line
under "Met outside the task", so the session receives it, and the retrospective's item on the
checker, `skill@knowledge-architect-retrospective@what-it-examines`, carries it to the workflow's
file. A reader of the format the harness documents as internal learns of a change only from the
sessions of the projects that use it, which `goal@knowledge-architect@the-workflow-improves-through-real-use`
relies on.

The route is the owner's choice between two shapes neither of which failed a constraint, over a
standing question of the retrospective, `rejected@agent-skills@retrospective-asks-for-unrecognised-lines`,
which every retrospective of every project would load and answer though most of their sessions
never ran the command. Its cost: it relies on the session carrying the header's line, or the
reviewer's report of it, into its retrospective.

### A retrospective is offered at a moment an event names, never at one the agent judges `##retro-trigger`

The retrospective is offered when one of three events occurs: a branch the session worked on has
merged into the main branch, a plan document has left, or the owner says the session is ending. It
runs only if the owner accepts. A moment named by an event can be followed by any agent where "a
moment it judges right" could not.

### A retrospective is offered at most once per session `##retro-offered-once`

The retrospective is offered once per session, at the first of the moments
`design@agent-skills@retro-trigger` names, and not again at a later one. Offering it once keeps it
from interrupting work.

### A retrospective asks standing questions, each on the decision or the goal it watches `##premortem-as-watch-points`

Every retrospective asks whether the session needed to change an installed skill or agent, whether the
session or one of its subagents acted as if a rule of the primer were absent, whether a project
skill's addition was missed, whether the session needed to write a reference or a path without
backticks because no checked form expresses it, and whether the session or a subagent wrote a script
or carried by hand over several steps a mechanical task the installed workflow asks of it. Real use
is the test of the workflow, per
`goal@knowledge-architect@the-workflow-improves-through-real-use`, and each question watches a
decision or a goal whose failure would be seen in real sessions before any check could see it:
`design@agent-skills@overlay-by-separate-skills`, the primer's delivery by an import line in
`design@core@owned-namespace-check`, `design@agent-skills@no-routing-table`,
`design@agent-skills@plain-text-is-no-repair`, and
`goal@knowledge-architect@mechanical-tasks-are-the-tool-s`. The last question is asked of every
session, since every session follows the workflow's procedures, where the question that lost in
`rejected@agent-skills@retrospective-asks-for-unrecognised-lines` met a command most sessions never
run; its evidence is real use, the owner's report that each design session wrote a loop to check a
slug free before `klarch id` existed, and the scripts with which half the searchers of one search filled their reports. The question on a
reference or a path written without backticks is the one channel by which a checked form missing from the checker, met in a consumer project, reaches this repository, since
the consumer's own entry for it is not citable here. The primer question asks about behaviour, on
the owner's direction that it ask a session directly what it observed of the behaviour, with no edit
of the subagent briefs. A session sees a subagent's brief and its report, not
its context, unless it reads the subagent's transcript, which `klarch transcript show --subagents`
prints: asked whether the primer reached the subagents, four received retrospectives answered
that it could not be observed, or was assumed, as the issue closed in commit 0a3c1a6 lists, read
with `git show 0a3c1a6^:crates/agent-skills/docs/open-issues/the-primer-question-cannot-be-answered-for-subagents.md`. The skill never states how many questions there are, so adding one changes no count.

### A retrospective's files go where the owner directs, and nothing of them leaves the machine before the owner's reading and word `##retrospective-destination`

The owner reads both files verbatim and may edit them. The workflow's file can become a public
issue on another repository, and a finding written in a session can carry the project's content, so
nothing of either file leaves before the owner has read it. On the owner's word, and where the owner
directs, the workflow's file becomes an issue on knowledge-architect's repository, through `gh` or
by the file and the address, and the project's file goes to an intake, per
`design@agent-skills@project-file-goes-to-an-intake`. The repository is the workflow's own
upstream, the one name of a project the shipped text holds.

### A kept finding of a retrospective's project file is analysed by an intake before it becomes an issue `##project-file-goes-to-an-intake`

The project's file goes to an intake, `design@agent-skills@intake-skill-home`, which analyses each
finding before anything changes in the project, since the analysis finds what
a direct entry would record wrongly: a finding already repaired, already recorded, resting on a
false premise, or proposing a fix that would reverse a recorded head. The direct path is
`rejected@agent-skills@retrospective-finding-straight-to-issue`, with the measurement that
defeated it.

### The intake of a retrospective's findings is an activity with an installed skill of its own, apart from the retrospective `##intake-skill-home`

`skill@knowledge-architect-retrospective-intake` analyses a project's own retrospective files
finding by finding, writes the analysis, and puts each finding to the owner with its evidence and a
default outcome. The retrospective writes the files; the intake takes them later, on the owner's
word. `goal@agent-skills@one-skill-per-activity` names the intake among the workflow's activities.

The two produce different artifacts, two files outside the project and an analysis inside it,
which makes them two activities by the dispatch rule of
`skill@knowledge-architect-agent-configuration@where-text-goes`. They also run at different
moments. The owner's account of the practice: an intake runs on the owner's word, nearly never
right after the retrospective unless a finding is critical, usually in a fresh session with no
memory of the work, on several files at once and on a later branch. The intake applies again while
its outcomes are carried out, on branches the retrospective's trigger does not name. So the
retrospective offers no intake at its own end: the project's file waits where its files went until
the owner hands it to an intake. The nearest
rival, a section of the retrospective that avoids describing twice how the report is read, loses
on that practice: a session with no session to examine would load the procedure for examining one,
and every retrospective offer would load the intake. The intake hosts the report's format and the kinds of a defect as fragments the retrospective
hosts too, so each is written once, and points to the retrospective's expectation sets and to its
form for citing a finding; the goal's measure admits it, since an agent reads another skill only at a step that points to it. A project adds to the intake through a skill
of its own, per `design@agent-skills@overlay-by-separate-skills`.

### A project's intake analyses only its own retrospective file, reading the workflow file only for the other side of an interaction finding `##intake-takes-the-project-file`

The installed intake takes the project's file of a retrospective, any number at once. The workflow
file of the same retrospective is read for the other side of an interaction finding, whose id names
the other file's, and nothing of it is resolved; it is written to only under the outcome of
`design@agent-skills@installed-fix-goes-upstream`. The workflow file goes upstream, per
`design@agent-skills@retrospective-destination`.

A consuming project does not do the workflow's own job. The checks that judge a workflow finding,
whether it still applies, whether it is already recorded, whether its fix reverses a recorded head,
read the workflow's history, design homes and rejected alternatives, which a consuming project does
not hold. The nearest rival, a triage of the workflow file in the project before it is sent, would
filter lapses and could check none of that history. The workflow file is read for an interaction
finding's other side because that finding has one id in each file, each naming the other.

### A finding whose fix lies in the installed text or in the checker is sent upstream, added to the workflow file or to the issue that carries it `##installed-fix-goes-upstream`

A finding of the project's file whose fix lies in the installed text or in the checker takes the
outcome "sent upstream". Where the retrospective's workflow file is not sent yet, the finding is
added to it, with the next number of its letter, its id and the project file's each naming the
other. Where the issue that carries the workflow file exists and can be edited, its body is edited
and a comment names the added finding, so that those who follow the issue see it. Where neither
applies, a new issue carries it. Two premises are assumptions, not measured: that the author of an
issue can edit its body, and that a body edit notifies nobody where a comment does. Nothing leaves
before the owner has read it, per `design@agent-skills@retrospective-destination`.

The set is closed to the two: the installed text, which the project never edits, per
`design@agent-skills@overlay-by-separate-skills`, and the checker it pins are the text and code a
project takes from the workflow without owning them, and the workflow's repository, which the
outcome reaches, maintains both and nothing else. The three other outcomes each lose such a
finding: handled now, it has
nothing the project can edit; as an issue, it sits in the project's register, where it cannot
close and which the upstream cannot cite, per `design@agent-skills@premortem-as-watch-points`; as
no change, it is dropped. The audit sends its findings on the installed text upstream for the same
reason, per `design@agent-skills@audit-outcomes`. The action, an edit of the workflow file or of
the issue that carries it, is the owner's.

An item a session meets outside its task whose fix lies there takes the same route, per
`primer@met-outside-the-task`: it goes to the workflow's file of the session's retrospective, and
the project's table of outcomes gives it neither a fix nor an issue entry, for the reason above. What
the project adds to the installed text or to the checker, a skill of its own or a check its own
build adds, is the project's own text and code, and an item on it takes the table's rows. The
route is stated in the primer because the primer is the one text every session holds when it meets
such an item, where the retrospective, the intake and the audit reach only a session that runs one
of them; the owner saw sessions spend time and effort deciding where such an item goes, and some
open it as an issue entry of the project. The route for such an item is the owner's: the owner
chose the retrospective's workflow file as its destination, and accepted for now that the item is
lost when no retrospective follows, as
`issue@agent-skills@an-item-kept-for-the-retrospective-is-lost-when-no-retrospective-follows`
records. The issue entry that `primer@where-knowledge-goes` asks for beside a pointer no checked
form expresses is still opened in the project, since that pointer must sit beside a reference the
project's checker resolves; the gap it records goes upstream all the same.

### An analysis of a project's retrospective file is committed with the owner's ruling on each finding, and leaves with its last outcome `##committed-intake-analysis`

The analysis is one file per analysed file in docs/retrospective-reports/ at the project's root,
which no checked form names, per
`issue@agent-skills@pointers-written-bare-to-clear-a-finding-reach-no-check`,
named by the analysed file's stem, a row of the primer's knowledge table, per
`design@agent-skills@knowledge-table-home`. Each finding's section ends with a default and the
owner's ruling, except a section that points to a cluster analysed in another file, which takes the
ruling given there, so that one ruling is given once and cannot differ. The file is committed once every ruling is in it, before any outcome is carried
out; the issues it rules are opened and the findings handled now are handled, in the commits their
routes need; the commit that carries out its last outcome, or a later commit of the same branch,
deletes it. The skill fixes no order of those commits, per
`goal@agent-skills@installed-text-leaves-room-to-judge`.

It takes the shape of the audit's report file, `design@agent-skills@committed-audit-report`, whose
argument holds here: the commit messages alone keep the outcomes and lose the evidence each ruling
was given on. A home each project chooses loses too: the skill could name no path, and the primer's
last row, to ask the owner, would fire at the first intake of every project.

### An intake marks the received project file it analysed once the analysis leaves `##received-file-marked`

Once every outcome of an analysis is carried out and the analysis leaves, the installed intake
writes a line at the head of the received project file: that it was analysed, that every outcome
was carried out, and the `git log` command that finds the analysis. The file stays where the owner
keeps it. The rule is the owner's. A directory of received files can hold files an earlier intake
analysed, which only the history of docs/retrospective-reports/ at the project's root tells apart, a
path no checked form names, per
`issue@agent-skills@pointers-written-bare-to-clear-a-finding-reach-no-check`; a marked file is not
handed to an intake again.

### A retrospective's project file names the project's main commit, which its workflow file names only where the project builds the checker from source `##version-line-names-the-main-commit`

The version line of the project's file names the main commit the session's tree contained when its
work began, as the session's first look at the tree reported it, the branch the session worked on, and whether the tree held uncommitted changes, beside the version of
knowledge-architect both files name. No commit of the branch is named, since a merge that rewrites
the branch's commits leaves it pointing at nothing, and no commit of the main branch after the
merge is named either: it holds the session's own work, so the intake would read the blamed text
with the session's repairs in it, and a rebase merge can replace it. The intake reads the blamed text at that commit
before reading it on the main branch, so the reason is respected at the retrospective's version
line and at the intake's check of whether a finding still applies.

Naming the commit stands on the owner's weighing, hedged, that the small saving of time and effort
it gives everyone is worth it, at no cost. It is absent from the workflow file because that
file may become public and holds nothing of the project beyond what a finding needs, per the
retrospective's rule on its two files, the upstream has no use for a consuming project's commit,
and the intake that reads the commit reads the project's file.

### The intake judges a fix of agent-facing text by the standard every writer and judge of that text applies `##intake-shares-the-admission-standard`

`skill@knowledge-architect-retrospective-intake` judges a finding's fix by
`skill@knowledge-architect-agent-configuration@admission-standard`, read whole where it shapes a
fix, and by its lapse rule where it judges a finding's kind: the need test, the evidence an
addition needs and the kind of a gap, the lapse rule, the repair by cause with its instruction
count and net growth, and the record check. This repository's intake of received files, which
follows the installed one, judges by the same standard. What admits a finding is the intake's own: a real
session behind each finding, and the owner's ruling on every finding.

The direction is the owner's: the owner judged it important, as the owner's view, that the intake
analyse findings and repairs on the same standard as the workflow. The evidence that admits a
finding differs between an audit and the intake: the intake has a real session behind each
finding, as `design@agent-skills@behaviour-additions-need-real-use` asks of an addition, and an
audit never has one. The worth of a fix and its shape do not differ, since both decide edits to the
same text at the same cost. The standard's home is the agent-configuration skill, per
`design@agent-skills@admission-rules-home`, and the intake hosts its four fragments, with the rule on a text's size cost, which the step that shapes a fix and the check of a
finding's kind point to, before any edit is written.
