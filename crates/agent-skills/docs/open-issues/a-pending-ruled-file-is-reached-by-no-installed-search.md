# A pending audit report or retrospective analysis is outstanding work that no installed search of what is already known reads

## Summary

The primer's knowledge table makes two directories at a project's root the homes of a file of
the owner's rulings that leaves once its outcomes are carried out: docs/audit-reports/, for each
pass of a project audit, and docs/retrospective-reports/, for each analysis of a retrospective's
project file. While such a file stays, it holds ruled outcomes no commit has carried out. The
installed places a session reads for what is already known name the issue and tripwire listings
only. A design could then be discussed, or a slice audited, past a ruled outcome of a pending file.
This is a prediction: no real session has shown it. The moment is narrow for an audit report, which
normally leaves on the audit's own branch, and is the normal case for an analysis, which stays on
the main branch across branches until its last outcome is carried out.

## Details

### What

Texts read, at the commit "The project audit counts convergence on old text, checks each repair
against the record, and commits each pass's report file", on which the sixth pass of the first
agentic-workflow audit ran:

- `primer@where-knowledge-goes`, the row "the evidence of one pass of a project audit, and the
  owner's ruling on each of its items": its home is one file per pass in docs/audit-reports/, as
  `skill@knowledge-architect-project-audit@record-of-an-audit` says, and it leaves when "the commit
  that carries out its last outcome, or a later commit of the same branch, deletes it". Read on the
  branch that shipped the intake, after that commit: the row "the analysis of a retrospective's
  project file, and the owner's ruling on each of its findings" gives docs/retrospective-reports/
  the same life. The analysis is committed before any outcome is carried out, as
  `skill@knowledge-architect-retrospective-intake@after-the-ruling` says, and its findings handled
  now are handled "on the same branch or on the branches that follow it", as
  `skill@knowledge-architect-retrospective-intake@analysis-and-ruling` says.
- `primer@verify-before-relying`, its subsection "Check whether it is already known": before
  diagnosing, `cargo klarch issues`, `cargo klarch tripwires` and `cargo klarch show`.
- `skill@knowledge-architect-issue-tracking@outstanding-across-registers` and
  `skill@knowledge-architect-issue-tracking@read-before-diagnosing`: the listings.
- `agent@knowledge-architect-record-searcher`, the search that
  `skill@knowledge-architect-design@discussion-loop` step 1 and
  `skill@knowledge-architect-planning@working-a-slice` point 2 dispatch: it reads the entries of the
  registers that `klarch worklist` lists, and no pending file.

A search for "audit-reports" over the installed text, `grep -rn audit-reports` over
`path@agent-skills@content/`, finds the primer's row, the audit skill's file name and the audit
workflow's preflight, and no search of what is already known. In this repository,
`instructions@verify-before-relying` lists `path@knowledge-architect@docs/audit-reports/` among the
places to look before diagnosing; an adopting project has no such line unless it writes one.

**How a pending file reaches a session other than its writer.** Every outcome of
`skill@knowledge-architect-project-audit@finding-outcomes`, and of the agentic-workflow axis's own outcome
table, is carried out in the audit's branch; an item the owner defers, or does not rule on when
the audit stops, becomes an issue entry. So a report file is normally deleted before the audit's branch merges,
and no installed text names a route by which a pending report file reaches the main branch. The
predicted moment is therefore a session that works on the audit's branch while a report file is
pending and did not write it, or a branch that merged with a report file still present. Not
established: whether either occurs in practice.

In this repository, `instructions@verify-before-relying` also lists
`path@knowledge-architect@docs/retrospective-reports/`, where this repository keeps its analyses of
received workflow files beside those of its own project files. The home of an analysis of a
project file is an installed row of the primer, so the installed text could name both directories
in one place.

Two repairs were considered for the analyses and not made, since each adds an instruction on a
prediction: naming the directory at the grounding of a design and at the design audit of a slice
or a spec, as well as before diagnosing; and opening an issue entry for every outcome ruled "handle
now", which the intake rules out, since such a finding "needs no issue entry", so as not to keep one
piece of work in two homes.

Reported by the L2 and L4 lenses of the sixth pass, as a predicted gap; the same gap for this
repository's analyses was reported by the L6 lens of the third pass. Not repaired by an edit,
since an instruction about how an agent behaves is added on evidence from real use, per
`design@agent-skills@behaviour-additions-need-real-use`.

### Why it matters

`design@agent-skills@record-searched-before-the-work` searches the whole record before the work is
designed, so that a standing entry the work bears on is ruled before
the code is written. A pending file's ruled outcome is outstanding work of the same weight that
the search does not reach. A design that duplicates or contradicts it costs the work twice. In this
repository, `design@knowledge-architect@committed-findings-analysis` keeps an analysis of a
received file until its last outcome is carried out, on the premise that the work it records is
found while it waits.

### What would close it

A retrospective of a session, in any project that keeps a pending audit report or analysis, that
discussed a design or audited a slice or a spec bearing on one of the file's ruled outcomes. Either
the session found the file, and the entry closes with no change; or it did not, and the installed
text names docs/audit-reports/ and docs/retrospective-reports/ in one place, the listing of
`skill@knowledge-architect-issue-tracking@outstanding-across-registers`, which the primer's check
and the record search then point to, rather than in each of them. That fix makes the search read a
place its head's argument does not cover, the entries of the record: it is a change of
`design@agent-skills@record-searched-before-the-work`, argued under
`skill@knowledge-architect-design` before its text is written, per the backstop of
`primer@design-heads`.
