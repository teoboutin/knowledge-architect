# No command searches the record's entries by keywords, and no command lists the mechanical work of an audit's method

## Summary

Two commands over the scanned record, which need the model and no check, are known to be missing.
A session that searches the entries greps the project, and a session that runs an audit's method
builds by hand the work lists its mechanical steps need. The owner named both as leads for the
commands that read the model.

## Details

### What

- **A search of the entries by a list of keywords, reporting the closest matches**: the owner
  asked for a search algorithm, more efficient than a grep of the project, that ranks the entries
  by how closely they match the keywords.
- **Mechanical work lists for the audit's method**, the design-record axis's first among them: the
  lists an audit axis builds before its agents judge, which a command could compute from the entity
  table, as `klarch worklist` computes the record search's.

Both read the model and run no check, so the milestone places them in its `query` Component. Neither
is designed: which keywords, which measure of closeness, and which axis's lists, are open.

### Why it matters

`goal@knowledge-architect@tasks-a-tool-does-better-are-the-tool-s` gives a published crate each mechanical
task the workflow asks of a session once its owner takes it in, which the owner has not done for either
of these, and the owner holds that the keyword search is a case that goal does not cover, per
`issue@knowledge-architect@the-mechanical-tasks-goal-omits-what-a-helper-does-better`. A grep misses an entry whose words differ from the search's,
and a work list built by hand can drop an entry, as `issue@query@no-command-lists-the-standing-entries-citing-a-set-of-entries`
records for another list.

### What would close it

A design discussion under `skill@knowledge-architect-design` for each command, then each built in
the crate that holds the commands over the model, with a test over a mock project.
