## Threads

### A. The status and recording of split decisions

**#split-guidelines-not-rules.** Your statement already holds for Components and for code. One nuance concerns design subjects. Their standard has two triggers, and they are of two natures:
- **The worklist bound is not a guideline.** Above it, a search agent cannot read its cluster whole. That is a measured limit of the tool, so it rightly reads as a trigger.
- **"Parts that change apart"** is the guideline.

I propose to keep both, and to say so in the text, so that the bound does not get softened along with the rest.

**#component-split-argues-the-criteria.** The head that argues a Component's existence, or a layout kept against the criteria, takes one line per shipped criterion:

```markdown
- one purpose: met — <why it pays here>
- independent reason to change: departed — <the argument, or the cost accepted>
- signals against a split: <which ones were weighed, and why none prevails>
```

The instruction lives in component-creation step 3, and the decision-record reviewer judges it there. That makes two sites, so the instruction earns a head in `agent-skills`. This also rewrites SKILL.md:166 so it means "a Component that departs from a criterion", which removes the second reading of "kept".

**#in-crate-split-unrecorded.** My reading of your words: a module split is *decided at design time*, written in the plan document as a step of its own, and *earns no head* unless one of the tests in `primer@design-heads` holds. Its reason goes in a comment at the module and in the message of the move commit. In this repository a module split never passes test 1, since the facade in `design@knowledge-architect@api-facade` keeps public paths unchanged. That reconciles "a split is a design decision" with "it needs no record". Correct me if you meant something else.

### B. The guidelines

**#module-split-guidelines.** These are new guidelines for cutting a crate into modules, with size demoted to a signal. The proposed criterion is thaum's, generalised: **a module holds what one review reads against one reference**. The reference can be a design head, a section of a specification, an invariant set, or one external effect (as in `design@git@git-is-asked-through-one-module`). The signals:

| signal | the failure it prevents |
| --- | --- |
| a second reference enters the module | a review that reads code outside its subject (thaum had 16 modules above its threshold) |
| two parts change apart, counting the changes the goals predict | unrelated diffs in one file |
| an invariant can only be protected by a visibility boundary | a helper widened to the whole crate |
| **against a split**: two parts every change reads together, such as a process and its mutations | fragmentation: one review across two files |
| **against a split**: one item, such as an enum, is large by itself | moving code does not divide an item; dividing it is a design change |

Size keeps exactly one role. It is not a number we pick: it is "a file a session cannot read whole in one pass". That is the argument the decision-recording skill already uses for turning a design home into a directory. thaum's 800 lines has no recorded basis, per commit 3997f0d1.

The text stays language-neutral, to respect the no-Rust-idiom head. It also adds a procedure: the split is a **move-only commit** that comes before the work, so that the review reads the work.

**The design subjects need no new guideline**, only the moment below.

### C. When splits are decided

**#splits-planned-before-work.** Two scouts, dispatched on the full path:

```
design grounding (code side, a design decision)
  └─ code-split scout: for each module/Component the draft touches,
     does the work push it past a signal of #module-split-guidelines
     or of component-creation? → a thread in the discussion
planning (record side, decides nothing)
  └─ record scout: `worklist` notices on the subjects the harvest
     writes into; subjects whose heads will answer parts that change
     apart → a step or slice "split subject X", before the harvest
```

The design audit of each later slice reruns both over that slice's area, since the code moves between slices. A split the scouts find goes into the plan as a step, or as a slice when it is large. It is never left as an issue.

**#pre-harvest-conformance.** The plan gets a new row under "What is already decided": **the heads the harvest touches without reversing them**. For those heads, one `agent@knowledge-architect-design-record-auditor` is dispatched with a narrow brief, not a whole audit. Each non-conformant head gets a step that conforms it before the harvest. One limit you should know: bringing a head into conformance is not always only a move. Writing the missing argument of a head, or the constraint it takes from a goal, can be a decision, so such a step can owe the design skill or your ruling.

### D. Plan documents

**#plan-document-directory.** Every plan document becomes a directory. This reopens the rival recorded in `design@model@spec-file-is-an-anchor` ("Making every spec a directory was the rival"). The new argument is that a plan document now has artifacts with no other home.

**#harvested-slice-kept.** A slice spec stays in the milestone directory once it has landed, marked `harvested`. A citation of it from outside the milestone directory is refused, and the checker does not judge the references inside it.

This reverses `design@agent-skills@plan-document-leaves-at-landing` at the slice level. The `harvested` marker defeats the "no marker" half. Freezing its references defeats the "breaks at every reversal" half.
