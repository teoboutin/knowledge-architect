## Threads

**#changelog-per-component**: your proposal. Each published crate's directory holds its own `CHANGELOG.md` with only its entries, in the same layout: `## Next release`, then `## <version>`. I support it. Its nearest rival is today's single shared file, and that loses on size (155 049 bytes × 12 identical files) and on noise for a lower crate's reader. One addition: the root Component holds a source file for entries that cover every crate (finding 3), which is **#cross-crate-entries**.

**#changelog-the-pin-reads**: what the binary crate ships, given finding 1. Two shapes:

- A (default): `crates/cli/CHANGELOG.md` is the assembled file, written by `cargo x changelog`, and `cli`'s own entries live in a source file under another name.
- B: `cli` ships its own `CHANGELOG.md` and also the assembled file under another name, say `CHANGELOG-ALL.md`, and the setup skill names that file.

A keeps the skill's path unchanged. Its cost is that `cli` is the only crate whose `CHANGELOG.md` is not its own. B gives every crate the same rule, but it changes the installed setup skill and adds a second shipped file. Either way, the root `CHANGELOG.md` is the same assembled bytes for GitHub readers. It has to be committed, because `rejected@knowledge-architect@changelog-copies-written-at-packaging` measured that cargo refuses an ignored file listed in `include`.

**#assembled-changelog-layout**: the order of headings. You proposed version, then component. The rival is version, then subsection, then component:

```markdown
## 0.11.0                          ## 0.11.0
### check                          ### Migration
#### Migration                     #### check
- minor: …                         - minor: …
#### New features                  #### agent-skills
…                                  - patch: …
### agent-skills                   ### New features
#### Migration                     #### check
…                                  …
```

The left layout (yours) is the per-crate files joined with no change. The right one groups every Migration entry of a version in one block, which is the block a pin move must act on (step 2 lists those entries). My default is the right layout, because the assembled file's one reader is the pin move. The cost is that the assembled file is a re-sort, not a join.

## #changelog-the-pin-reads, and where the assembled file lives

I agree there should be no second copy of the assembled file. Here is a shape that gives you a single assembled file and still needs no network at a pin move:

- **The assembled file exists once**, at a path the project sets, which defaults to `CHANGELOG.md` at the root. People read it there, on GitHub or in a checkout. No crate ships it.
- **Each crate ships its own small `CHANGELOG.md`**, which is its source.
- **The pin move reads the crates' own files from the registry**, the ones cargo already unpacked. It does not fetch the root file from GitHub.
- **Each crate's file is not mistaken for the whole history.** Its preamble says it holds only that crate's entries, and gives the URL of the assembled file. The URL is built from `repository` in Cargo.toml plus the configured path. The check asserts that this line is current, so it cannot go stale.

Why I would not have the pin move read GitHub:

1. **The network may not reach it.** In a Claude Code cloud environment, package registries are reachable by default and other hosts only when an environment lists them. I read this in this session's own environment tool descriptions; I did not test it on a consumer's environment. crates.io is reached anyway, because the pin move fetches the crate.
2. **The URL is not always known.** A GitHub URL needs the project's `repository` field and a tag naming scheme. A path in the registry needs neither.
3. **It removes nothing that a person can read today.** People still read the root file. Only the agent's step reads locally.

One cost: the agent reads one file per crate, about twelve here, instead of one. If that proves to be a burden, a later option is a `klarch changelog --since <version>` command that assembles from those registry sources. I am not proposing it now.

**Location: by path, not by component.** The root is not a published crate here, and in a project with a single crate the assembled file would be that crate's own file. A path covers both cases, a component covers neither. Default: `[changelog] assembled = "CHANGELOG.md"`. A project with one published crate omits it, and no file is assembled.

## #changelog-bump-check: new, from your example

The check reads only the files in the tree. It needs no history.

- **Per-crate versions:** in each crate's file, the class of a released section implies its version, compared with the previous section in the same file.
- **Lockstep** (`version.workspace = true` in every crate): the comparison runs over all crates together, since one version's highest class is across every crate. Here a crate's file can skip a version, such as gates having 0.9.0 and then 0.11.0.
- **Under 0.x**, major and minor both bump the second number, as Cargo treats them.
- A file with no classes, 0.1.0 here, is exempt. Whether such an exemption is declared or inferred is an open detail.

This settles #absent-version-section: a version with no entries is omitted from a crate's file, and the lockstep comparison uses the versions all files hold together.

## #changelog-holds-no-citation and #citation-free-paths

I agree with your position: no reference in any changelog file, crate or assembled. What I found when I looked at the precedent:

- `##crates-io-page-file` says the page "holds no backticked reference", but no check enforces it. `grep -rli crates-io crates/*/src` finds no code, and the manifest has no row for it. So the rule exists today only as a sentence in a design head, and that is a second member for your feature. It is not a new case.

Proposed shape:

```toml
[walk]
citation-free = ["crates/*/CRATES-IO.md", "crates/*/CHANGELOG.md"]
```

- In a matched file, a span that parses as a reference is a finding **whether or not it resolves**, and no span there is resolved at all. A placeholder in angle brackets, such as `design@<anchor>@<id>`, is an illustration and passes, as the primer already says. That keeps the syntax examples, which were the reason `##the-changelog-is-outside-the-walk` gave for keeping the changelog out of every check.
- The assembled file is generated from the checked sources, so it is not matched. Each finding is reported once, in the crate file it comes from.
- A future render site that wants clickable links changes this one line of configuration, not the design.
- Released sections: the about 77 lines with an `@` span are respelled as plain text in the conversion. That is a structural change, on your reading.
- Knock-on effect: `##changelog-entries` and `design@agent-skills@audit-triggers` make a Migration entry cite an audit axis's section "as a reference", and the installed setup skill looks for exactly that. Both change to an entry that **names** the axis in words, such as "the design-record axis of the project audit". The setup skill then lists the entries that name an axis. The rival was a dedicated category such as `Audit`. It loses because a single entry is both a Migration and an audit trigger, and a category can be only one.

## #no-history-beyond-the-branch: a root head

It goes in the root's design home, since it constrains every later check and gate, as you said. Draft title:

> No check reads the history before the base of the branch it judges

The argument:
