# Workflow authoring reference

A workflow structures work across many agents — to be comprehensive (decompose and cover in parallel), to be confident (independent perspectives and adversarial checks before committing), or to take on scale one context can't hold (migrations, audits, broad sweeps). The script is where you encode that structure: what fans out, what verifies, what synthesizes.

When you do call it, the right move is often **hybrid**: scout inline first (list the files, find the channels, scope the diff) to discover the work-list, then call Workflow to pipeline over it. You don't need to know the shape before the *task* — only before the *orchestration step*.

## Short answer

Yes, the workflow can generate the work list itself, though the script cannot run the command directly. Per the authoring reference, a workflow script has "No filesystem or Node.js API access": it only spawns agents. So the first step is a small agent that runs `klarch worklist --out` and returns the list of `agent-<n>` directories through a schema. The three audit workflows already do this: their preflight agents run `{{command}} issues` and `{{command}} tripwires` (`crates/agent-skills/content/workflows/design-record-audit.js:280`).

With that, the session's whole part shrinks to three acts:

1. Choose the inputs: the work files, the subjects, the seeds. These are judgements only the session can make.
2. Start the workflow.
3. Act on the verdicts it returns. These acts route decisions, so per `design@agent-skills@session-acts-on-the-verdicts` they stay with the session.

## Proposed shape

```js
// knowledge-architect-record-search
// args: { scratch, work: [paths], subjects: [ids], seeds: [refs],
//         since?, seedsFrom?, bound?, maxRounds? }

phase('worklist')
const list = await agent(
  'Run {{command}} worklist --out ' + dir + flags(args) + '. Return the agent directories it wrote, ' +
  'or the command\'s refusal verbatim.',
  { effort: 'low', schema: { agents: [string], refusal?: string } })
if (list.refusal) return { refusal: list.refusal }          // e.g. a seed naming no entry

phase('search')                                             // harness caps concurrency, ~16 at once
let reports = await parallel(list.agents.map(a => () =>
  agent(brief(a, dir + '/work.txt'),
        { agentType: 'knowledge-architect-record-searcher',
          schema: { written: bool, reportText?: string } })))   // text when the harness refused the write

phase('verify')                                             // loop: verify, send back the failures
for (let round = 1; ; round++) {
  const v = await agent('Write each returned reportText into its report.md, then run ' +
                        '{{command}} worklist --verify ' + dir + ' and return each failing agent with its findings.',
                        { effort: 'low', schema: { passed: bool, failing: [{ agent, findings }] } })
  if (v.passed) break
  if (round === maxRounds) return { failing: v.failing }    // no silent cap
  await parallel(v.failing.map(f => () => agent(resendBrief(f), { agentType: SEARCHER, ... })))
}

phase('cross-check')                                        // optional: see #verdicts-verified-in-the-workflow
...
return { verdictFiles, generatedLines /* or gaps + fitLines */, closingSections, ownerQuestions }
```

The session then calls it like this:

```
Workflow({ name: 'knowledge-architect-record-search',
           args: { scratch: '<scratch>/search', work: ['<draft>'],
                   subjects: ['thread-a', 'thread-b'], seeds: ['design@x@y'] } })
```

## Threads

**#search-runs-a-saved-workflow.** The search ships as a saved workflow, one per occasion family. The four occasions the searcher's description names (a design grounding, a retrospective intake, the design audit of a slice or of a spec) differ only in their flags. `--seeds-from` switches the outputs to `gaps.md` and `fit-lines.md`, so one script covers all of them.
- **Rival:** the rewording of the dispatch sentence from the intake's subject `searcher-dispatch-exceeds-harness-cap`.
- **What defeats it:** you took in the generic part of the 36-agent workflow, and a rewording still leaves 24 to 36 hand dispatches and checks per search.

**#workflow-runs-the-worklist.** This is your question. An agent at low effort runs `--out` and returns the directories through a schema.
- **Rival:** the session runs `--out` and passes the directory in `args`. That costs the session one command and one decision about flags, and the session must already know those flags to fill `args`. So the rival saves nothing and adds a step.
- **Consequence:** a refusal by `--out`, such as a seed that names no entry or a work file it cannot read, comes back as the workflow's result, and the session repairs its args and starts the workflow again.

**#report-loop-in-the-workflow.** Today the session does three things by hand: it writes text-returned reports into their files, runs `--verify`, and sends back the agents whose reports fail. The workflow does all three, up to `maxRounds` rounds (default 3), then returns what still fails. It never repairs a report itself, because the dispatcher may not repair one, per `design@agent-skills@one-record-searcher`.
- **Assumption, to check by one probe:** that a searcher run inside a workflow meets the same refusal of `Write` as one dispatched by hand. That probe is the harness's mechanics, which the root `CLAUDE.md` admits.

**#closing-sections-file.** The `## Decided` and `## Met outside the task` sections of every report reach the session as one file.
- **My default:** `--verify` writes the file, which is shape 1 of the query issue, and closes that issue in the same work. A command does this better than an agent copying text (`goal@tasks-a-tool-does-better-are-the-tool-s`).
- **Rival:** an agent of the workflow gathers the sections. That needs no Rust change, but it is the kind of copy that missed sixteen reports before.

**#verdicts-verified-in-the-workflow.** This is the open question with the biggest effect on what the session still does. `design@agent-skills@session-acts-on-the-verdicts` requires an independent check of each verdict other than `unrelated` before the session acts on it, and allows the session to hand that check to an agent.
- **Proposal:** a cross-check stage, one agent per `verdicts-<subject>.md`, that tries to refute each verdict and returns the refuted ones. The session then reads only the verdicts that survive, plus the refutations.
- **Cost:** about one more agent per subject, and the verifier must read the work files too.
- **Rival:** keep the check with the session. That is cheaper in agents, but it is exactly the reading you want out of the session.

**#search-reads-a-fixed-tree.** The searcher's body says "You run in the session's tree, which nobody edits while you search". A workflow runs in the background, so the session could edit meanwhile.
- **Proposal:** the workflow states in its `description` and its result that the session edits nothing until it returns.
- **Rival:** a reading worktree at a commit, as the audit workflows use. That rival fails on uncommitted work: the draft of the work, and often the entries it changes, are not committed when the search runs.

**#dispatch-text-home.** The dispatch moves out of the searcher's description into the script, the same move the audit axes made.
- **What changes:** the description keeps what the session needs. That is the inputs to choose, the workflow's name and `args`, how to act on each output, and a line for a harness without the workflow: dispatch the steps by hand, as the script orders them.
- **Consequences:**
  - This rewrites part of `design@agent-skills@one-record-searcher` ("its description carries the dispatch"), so it needs `skill@knowledge-architect-decision-recording@reversal-check`.
  - The five skills that name the search (design, planning, retrospective-intake, retrospective, review) get re-pointed.
  - Each skill names the workflow, which is what counts as the opt-in the Workflow tool requires.

So a search returns two very different populations:

- **Verdicts that need an act**, about 1 to 11 per search. To act on a `check-reversal`, the session must read the entry whole and reason over it anyway. Checking the verdict costs almost nothing extra during that reading. This is also where the session's context matters most: whether the design really reverses a head depends on the shapes as argued in the conversation.
- **Light verdicts**, about 20 to 180 per search. The act is "keep the shapes within the quoted sentence". Most of the session's checking cost is here.

## What changes in each case

**Case A: the session verifies, as today.**
- The workflow returns the verdict files. The session reads every line other than `unrelated` with its quotation, and runs `show` where it doubts one.
- What this catches: above all a **downgrade**, a verdict graded `constrains, respect` that is really `conflicts, check-reversal`. Seeing it means knowing exactly what the shapes do, including what the conversation added after the draft was written.
- Cost: on the larger searches, 120 to 190 lines enter the main context, plus their `show` reads.

**Case B: a cross-check inside the workflow.**
- A verifier per subject reads the verdict files and the draft and tries to refute each verdict. The session gets the survivors plus the refutations.
- Per `design@agent-skills@at-least-one-independent-verification`, one verification is enough. So the session would act on survivors without checking them again.
- What the session still does: it must still know every `respect` constraint to keep the shapes within it. So it still reads the light lines and only drops its own checking of them.
- The weakness: the verifier sees exactly what the searcher saw, the draft and the record. It is a separate session, but it has the same information, so it cannot catch a verdict that is wrong only against the conversation.
- What escapes: a downgrade that escapes reaches the design-conformance reviewer at the earliest, at the plan's review or at the merge (`design@agent-skills@verdicts-reach-the-conformance-review`). By then the work may exist and the fix is rework.
- Cost: about one more agent per subject.

## A third shape: #verdicts-split-by-action

The two populations call for different readers, so I propose splitting them instead of choosing A or B for all verdicts:

- **Verdicts that need an act** go to the session, with their entries whole. The session verifies them while acting, as today. Both your worry and the measurement point here: few lines, highest stakes, the session's context decisive.
- **Light verdicts** go to the session as compact lines: reference, action, quotation. No entry text, and no cross-check by default. The session checks each line against the shapes it holds, which is cheap because the quotation is in the line, and runs `show` only where a line looks like a downgrade.

What the split changes compared with today:
- the session reads the light verdicts as lines with quotes, not as entry texts;
- no agent stands between the searchers and the session's judgement.

The cost is a change in what `--verify` writes: verdict files split by action, or a compact lines file. It sits next to #closing-sections-file in the `query` change. I have not checked how today's verdict files order their entries, so that detail is open.

## The experiment

`design@agent-skills@synthetic-evidence-not-built` limits what the experiment can be used for:

- **Allowed:** running this discussion's search with a draft of the workflow, a cross-check stage included. The head counts that as real use: "a record search that grounds a real design discussion with its searchers briefed in a proposed report form". The workflow's mechanics are also admitted as evidence: the worklist agent, the report loop, and whether a searcher meets the `Write` refusal inside a workflow.
- **Not allowed as evidence for choosing:** comparing the cross-checker's results with mine. One run is a sample of one, and agreement between two agents chooses no shape.
- **What it can still give:** a concrete miss confirmed by reading, such as a downgrade the cross-checker let through that the conversation shows is wrong, or one I missed that it caught. Such a miss counts as a misbehaviour observed in real use.
- **The asymmetry:** a miss would be evidence. No miss proves nothing. So the run can confirm your worry, but it cannot rule it out.

My default is to run it: the search has to run anyway, and the extra cost is a few cross-check agents. A second verification is allowed, since one is a minimum, not a ceiling. I will verify every verdict myself as in case A, independently of the cross-checker's output, and report each disagreement with the reading that settles it.
