# knowledge-architect goals: The two together

The goals that the documentation model, what is built on it and the workflow serve together.

## Agents work autonomously without drifting from the design recorded in their project `##agents-work-without-drift`

knowledge-architect lets AI agents carry a target project's work with less supervision. What they
build stays within the design the project has recorded: its goals, the decisions its record holds
with their arguments, and the reasons recorded beside its code and its agent-facing text. A
recorded decision, or a reason recorded beside code or agent-facing text, changes only by a change
that reverses it on purpose and argues the reversal. A
design the project did not keep comes back only by a change that reopens it on purpose.

Where two purposes of knowledge-architect compete, this one comes first. It never comes before the
decisions of the project's owner, the exchange with that owner and the check of that owner's word,
which `goal@knowledge-architect@the-owner-decides`,
`goal@knowledge-architect@design-with-agents-as-counterparts` and
`goal@knowledge-architect@the-owner-s-word-is-verified` state.

## The generic part of a tool or a procedure that a target project sets up or changes is shipped by knowledge-architect once knowledge-architect's owner takes it in `##generic-tools-and-procedures-are-shipped`

Work in one target project sets up or changes tools and procedures that make its development more
efficient or the project better, such as a gate, a maintenance command, a kind of reviewer, an
external survey, a testing method or a publishing method. knowledge-architect ships the generic part of one once
knowledge-architect's owner takes it in, so that every target project that has a use
for it, or is meant to, gets it. A part is taken in
by that owner's choice, and not because it is generic. What is particular to one project stays in
that project. So knowledge-architect is about more than keeping a project's documents.
