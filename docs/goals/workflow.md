# knowledge-architect goals: The workflow

The goals on the workflow that knowledge-architect installs for the agents of a target project.

## AI agents get a complete workflow for each activity of a target project whose generic part knowledge-architect's owner has taken in `##agents-get-a-complete-workflow`

The workflow covers the generic part of each activity that knowledge-architect's owner has taken
in, an activity that only some target projects carry out included. It is there to raise the quality
and the efficiency of the agents' work. It is complete: an agent carries each activity out with the
workflow and what its project adds, and needs no instruction from outside what knowledge-architect
provides and what its project adds. The activities
taken in include these, and the list grows:

- setting up a project;
- setting its goals;
- discussing designs;
- planning;
- recording decisions;
- tracking open issues;
- developing;
- working on a branch under a linear history;
- releasing;
- reviewing;
- auditing a project on one aspect;
- maintaining the agent configuration;
- the retrospective;
- the intake of a retrospective's findings.

## The workflow states what an agent needs to carry out the activities it covers, and leaves every other case to the agent's judgement `##only-needed-instructions`

The workflow does not try to cover every case. The situations an agent may meet under it have no
limit, and the agent's judgement is meant to handle those the workflow does not cover. A case that
judgement handles well enough gets no instruction, whichever goal the instruction would serve. So
the workflow does not grow without bound: it is not a text that gains an instruction for each edge
case or lapse found, so that no instruction leaves an ambiguity.

## The workflow leads agents to write better code in a target project `##the-workflow-leads-to-better-code`

What the workflow says about code and tests aims at code of better quality in a target project, the
code of its tests and of its maintenance tools included.

## The workflow leads a target project to be split into modular units, each with one purpose `##projects-are-split-into-modular-units`

A split matters at more than one layer of a target project: the project into its parts, the code of
one part, and the documents of its design by subject. Units that each serve one purpose make the
project easier to explore and to work in, since an agent reads one unit whole and changes one at a
time. They also make an agent's change easier for a person to review. One purpose per unit is a
direction, not a rule a unit fails alone: this goal fixes no rule of splitting.

## The workflow improves through real use `##the-workflow-improves-through-real-use`

Real use is a session that applies the workflow inside a real target project, on work meant to
merge into that project's main branch, under the supervision of a person who contributes to the
project or owns it. It is the test of how an agent behaves under the workflow. What real use shows
unclear, missing or wrong in the workflow reaches knowledge-architect and changes the workflow.
Where such a change is an owner's to rule, that owner is knowledge-architect's.

## The main session orchestrates agents that carry the work, and keeps its focus on the design and the decisions `##session-orchestrates-the-work`

The main session is the session that the person supervising the work exchanges with. It
orchestrates agents it dispatches to carry the work, and acts on what comes back, so that it can
focus on deciding the design with that person, and on reporting each decision taken. This goal does not say when a dispatch
happens, nor for which kind or size of work.
